## 0. 한 줄 요약

친구들끼리 하는 리그오브레전드 5:5 내전의 전적(KDA, 승률, 참여도)과 **토너먼트 드래프트 밴 순서**를 기록하는 웹 서비스.
경기 스크린샷을 AI로 읽어 기록하고, 로그인은 디스코드로만 한다. 밴 분석은 사용자가 직접 한다.

---

## 1. 목적과 이유 (사용자 진술)

- 친구들끼리 쓸 서비스지만, **실제 사용자가 있는 서비스**를 만들고, 웹 개발로 프로젝트 하나를 **완성한 뒤 계속 운영**하는 경험을 얻는 것이 목적.
- 거창하게 만들 생각은 없다.
- 이 목적에 대한 평가: 합당함. 실사용자 + MVP 출시 + 피드백 반영 + 운영 경험은 포트폴리오 방법으로 제시된다. 단, 근거는 블로그·커뮤니티 수준이고 "운영 경험이 합격률을 올린다"는 정량 근거는 찾지 못했다.
- 한계: 사용자 규모가 작아서 "트래픽 처리·확장성"은 주장할 수 없다. 가치는 **운영 절차를 실제로 돌린 경험**과 **실사용 피드백**에 있다. "운영했다"는 말은 운영 기간과 기록이 있어야 힘을 가진다.

## 2. 사용자

- **사용자 = 실제로 내전을 하는 인원.** 현재 약 19명이며 늘어날 가능성이 있다.
- 내전 전용 디스코드 서버가 있고, 내전 참여자는 모두 디스코드를 쓴다.
- 데이터 규모는 작다. 경기가 수천 건 쌓여도 인덱스 몇 개면 충분하므로 성능 걱정은 불필요.

## 3. 범위

### 원하는 것
- 선수별 **KDA**, **승률 랭킹**, **참여도**
- **밴 순서 기록** (토너먼트 드래프트). 분석은 사용자가 직접 하므로, 웹에 분석 기능을 넣기보다 **CSV 내보내기**(또는 읽기 전용 DB 접근)를 제공한다.

### 원하지 않는 것 (빼기로 함)
- 점수 공식, 시즌, 트로피, MVP/ACE 빈도 같은 파생 지표
- 그룹·초대 코드 (한 팀만 쓰므로 불필요)
- Redis Sorted Set 리더보드: 이 규모에서는 필요한 이유가 없다. 이유 없는 기술 나열은 면접에서 감점 요인이라 제외. 실제 문제가 생겼을 때 근거와 함께 추가한다.

## 4. 데이터 수집: 조사 결과와 결론

| 방법 | 결과 |
|---|---|
| Riot 공식 API (Match-V5) | 커뮤니티 문서에 따르면 커스텀 게임 데이터(토너먼트 시스템 제외)는 개인정보 정책 때문에 API로 조회할 수 없다. **이 문서가 최신인지는 검증하지 않음.** 확인 방법: 개발자 포털에서 키를 발급받아 친구 PUUID로 Match-V5 목록을 조회하고 최근 내전이 나오는지 본다. |
| 롤 클라이언트(LCU) 로컬 수집 | 실제 사례 있음(커스텀 게임 디스코드 봇 inhouse-bot 등). 하지만 비공식 경로이고 클라이언트가 켜진 Windows PC가 필요하다. 정책은 확인하지 못함. |
| 공식 토너먼트 API | 프로덕션 키 등 별도 심사 대상으로 보여 친구 내전용으로는 비현실적. 페이지 문구가 모호해 확신은 못 함. |
| **스크린샷 + 비전 AI** | **채택.** 수집 프로그램 설치나 비공식 API 의존이 없다. 참고 사이트(§5)가 이 방식으로 운영 중이다. |

### 결정 사항: 경기당 스크린샷 2장
1. **밴픽 화면**: 밴 순서를 얻기 위해 필요하다. 밴픽이 끝난 뒤 게임 로딩 전에 찍어야 하고, 게임이 끝나면 다시 볼 수 없다.
2. **결과창**: 닉네임, 챔피언, K/D/A, 승패.

> 결과창에 밴 정보가 어떻게 표시되는지, 닉네임에 태그(#KR1)가 함께 나오는지는 **확인하지 못함.** 샘플로 확인할 것.

## 5. 참고 사이트: naejeon.lol

- 결과창 스크린샷을 붙여넣으면 비전 모델(사이트 설명상 GPT-5)이 닉네임과 K/D/A/CS/골드를 읽고, **자체 학습한 YOLO 모델**이 챔피언 아이콘과 라인을 인식한다. 저장 전에 검토·수정 단계가 있다.
- 그 밖에 그룹 리더보드, 시즌, 내전 전용 지표, 팀 밸런서, 디스코드 서버 찾기가 있다. Google 로그인이며 Riot 계정과는 연동하지 않는다.
- 광고로 운영하는 1인 개발자의 무료 서비스이고 유료 멤버십을 예고했다.
- 확인한 범위는 **랜딩 페이지 텍스트까지.** 로그인 후 대시보드와 `/demo`는 보지 못했다.
- **기능과 흐름 아이디어만 참고하고, 코드·문구·디자인·로고는 따라 하지 않는다.**
- 시사점(추정): YOLO를 따로 학습시켰다는 것은 비전 LLM만으로 챔피언 아이콘 인식이 부족했을 가능성을 시사한다.

## 6. 로그인: 디스코드 OAuth2만 사용

- 필요한 권한
  - `identify`: `/users/@me`를 이메일 없이 조회. 저장할 개인정보가 줄어든다.
  - `guilds.members.read`: 특정 서버에서 내 멤버 정보(역할, 서버 닉네임, 가입일) 조회.
- 목적: **내전 디스코드 서버 멤버만 로그인 허용** → 외부인의 기록 오염 방지. 디스코드 역할로 관리자를 판별할 수도 있다.
- 흐름
  1. "디스코드로 로그인" → 디스코드 동의 화면
  2. 동의 → 디스코드가 인가 코드를 우리 서버로 보냄
  3. 서버가 코드로 토큰을 받고 `/users/@me`로 디스코드 ID 조회
  4. 내전 서버의 멤버 정보를 조회해 멤버인지 확인
  5. 멤버면 로그인 완료, 아니면 거부
- 구현: Spring Security OAuth2 클라이언트에 디스코드를 커스텀 공급자로 등록 (**일반 지식, 설계 때 확인**).
- 사용자는 **디스코드 ID**로 식별한다. 사용자명과 서버 닉네임은 바뀔 수 있다.
- 권한: 입력자 기록(`created_by`), 수정·삭제는 관리자만, 수정 이력 보관.

## 7. 데이터 모델 초안 (확정 아님)

```
player       (id, display_name, discord_id unique nullable)
player_alias (player_id, lol_name)          -- 한 사람이 여러 롤 닉네임을 가질 수 있음
game         (id, played_at, patch, winner_team, created_by)
game_player  (game_id, player_id, team, champion_id, kills, deaths, assists)
game_ban     (game_id, turn, team, champion_id nullable)
```

설계 원칙
1. **밴은 별도 테이블에 `turn`(순서 번호)으로 저장.** 밴 규칙을 코드에 고정하지 않고 "몇 번째에 어느 팀이 무엇을 밴했는지"만 기록한다. 밴을 건너뛴 경우를 위해 `champion_id`는 null 허용.
2. **챔피언은 Data Dragon 챔피언 키로 저장.** 이름이 바뀌거나 신규 챔피언이 나와도 분석이 깨지지 않는다.
3. **`patch` 저장.** 밴 분석은 패치에 따라 의미가 달라진다.
4. **선수는 `player_id`로 식별.** 닉네임이 바뀌어도 기록이 이어진다.
5. **선수와 로그인 계정 분리.** 사이트에 로그인한 적 없는 친구도 기록은 남아야 하므로 `discord_id`는 null을 허용하고, 처음 로그인할 때 연결한다.

### 닉네임 → 선수 매핑 흐름
1. AI가 결과창에서 롤 닉네임을 읽는다.
2. 서버가 `player_alias`에서 가장 가까운 이름을 찾는다. 후보가 20명 안팎이라 보정이 쉽다.
3. 그 선수의 기록으로 저장하고, 화면에는 `display_name`을 보여준다.

예외 처리
- **처음 보는 닉네임**(부계정, 닉네임 변경, 새 인원): 검토 단계에서 "기존 선수에 연결" 또는 "새 선수 생성". 연결하면 alias로 저장되어 다음부터 자동.
- **비슷한 닉네임**: 유사도가 기준보다 낮으면 자동 매칭하지 않고 사람이 고른다.
- **태그 미표시**: 게임 이름만 나오면 이론상 겹칠 수 있으나 20명 안팎에서는 가능성이 낮다.

## 8. 지표 정의 시 주의

- **KDA**: 경기별 KDA의 평균이 아니라 총 (K+A) ÷ 총 D. 데스 0인 경기가 평균을 왜곡하지 않는다.
- **승률 랭킹**: 최소 경기 수 기준 필수, 경기 수를 함께 표시. 19명이 돌아가며 10명씩 뛰므로 사람마다 경기 수가 크게 다르다.
- **팀 구성 편향**: 같이 뛴 팀원에 따라 승률이 달라진다. `game_player`의 팀 정보로 분석 시 보정 가능.
- **참여도**: 우선 "참여 경기 수 ÷ 전체 경기 수"로 정의.

## 9. 그 밖의 함정

- **챔피언 아이콘 인식이 가장 어렵다.** 대안: Data Dragon 공식 아이콘과 유사도 비교, 또는 MVP에서는 드롭다운 선택.
- **한글 닉네임 오인식** → 검토 단계 필수, alias 사전으로 보정.
- **비전 API는 수 초 걸리고 비용이 든다** → 업로드와 추출을 비동기로 분리. 경기당 비용과 정확도를 측정해 README에 수치로 남긴다.
- **입력 부담**: 수동이면 경기당 10명 × (챔피언, K/D/A) + 밴 10개로 필드가 40개 이상. 그래서 스크린샷 추출이 실질적인 가치.
- **친구 데이터 책임**: 수집 최소화, 비밀번호는 저장하지 않음(디스코드 인증에 위임).
- **부하 수치**: 실사용 부하가 작으므로 성능 수치를 포트폴리오에 넣으려면 k6 등으로 인위적으로 측정했다고 명시.
- **Riot API를 쓸 경우**(챔피언 데이터 외에 솔랭 티어 등): 개발자 포털에 제품 등록, "Riot이 보증하지 않음" 면책 문구 필요. 개인 키는 소규모 개인 사이트 용도.

## 10. 운영 체크리스트 (v1부터)

CI/CD, 모니터링·알림, 추적 가능한 로그 설계, DB 백업과 **복원 테스트**, 롤백 절차, 시크릿 관리, 월 비용 상한 알람.
장애·버그는 "원인 → 조치 → 결과"로 **운영 일지**에 남긴다. 운영 지표 예: 주간 등록 경기 수, 활성 사용자 수.
학기·자격증·지원 일정과 겹치므로 관리형 서비스와 자동화로 부담을 줄이고, 범위를 고정하는 "완료 기준"과 최소 운영 기간(예: 6개월, 임의 기준)을 미리 정한다.

## 11. 미결정 사항 (설계 세션에서 정할 것)

1. 밴픽 화면·결과창 추출이 쓸 만한 정확도인지 (샘플 실험으로 판단)
2. v1 입력 방식: 수동 입력으로 먼저 배포할지, 스크린샷 추출을 처음부터 넣을지
   - 이전 세션의 제안: 운영 시작이 늦어지지 않도록 v1은 수동 입력 + 기본 통계로 배포하고, v2에서 AI 추출을 추가. 사용자는 "스크린샷이 가장 무난할 것"이라고 했으나 v1 포함 여부는 확정하지 않음.
3. 픽 순서도 기록할지 (`game_pick` 테이블 추가 여부, 입력 화면도 달라짐)
4. 기존 포트폴리오 계획의 **운동 기록 API를 이 서비스로 대체할지** 병행할지
   - 이전 세션의 제안: 대체가 효율적. 인증·JPA·배포 기본기를 v1에서 익히고, v2의 AI 요소로 "AI 프로젝트" 자리도 겸할 수 있다. 두 개를 동시에 깊게 하긴 어렵다.
5. Spring Boot 학습 진도에 맞춘 착수 시점
6. 기술 스택 세부 (Spring Boot + MySQL 전제, 이미지 저장은 S3, AI 추출은 큐·워커 비동기 처리가 이전 세션의 제안)

## 13. 작업 방식 선호

- 한국어 존댓말, 간결하고 범위에 맞는 답변, 희망적이지 않은 객관적·현실적 평가, 효율 중시.
- 주장에는 신뢰할 근거를 붙이고, 확인하지 않은 내용은 확인하지 않았다고 표시.
- 기술 설명은 "어디서 어디로, 어떤 데이터가, 누구에게, 그다음 무엇이"의 단계별 흐름으로.
- 계획·가이드를 세울 때: 개념 설명, 실무 기반 이유, 파트별 오류·함정 점검 후 전체 연결 점검, 사용자 의견은 합당한지 판단한 뒤 반영.
