# ADR 009. 추출 작업은 "읽은 사실"만 저장하고, 단일 스레드 비동기로 돌리며, 재시작하면 실패로 정리한다

- 상태: 확정 (M4, 2026-10-20)
- 관련: `docs/design/m4-design.md` D1·D3·D4·§2.4·§11.2, `V3__extraction_job.sql`, 코드 `ingest/job/*`

## 배경

결과창 한 장을 Gemini로 읽는 데 20초~1분 반이 걸리고, 무료 등급이라 429·503이 잦다. 요청 안에서 기다리게 하면 브라우저 요청이 오래 묶이고, 실패를 다시 시도하기도 어렵다. 또 추출이 끝난 뒤 담당자가 선수·별칭을 고치면 "초안"이 낡을 수 있다.

## 결정

1. **사실만 저장**: `extraction_job.result_json`에는 화면 순서의 숫자·닉네임·박스와 아이콘 후보(상위 3개, 점수 차)만 넣는다. 선수 연결·A팀/B팀 판별·검증 같은 초안은 `GET draft`/`check` 때마다 현재 DB로 다시 계산한다.
2. **비동기 실행**: `@Async` 전용 실행기(스레드 1개, 대기열 2개)가 작업을 돌린다. 작업 행을 커밋한 뒤에 넘기고, 화면은 2초마다 상태를 조회한다.
3. **상태 전이는 조건부 UPDATE**: `QUEUED → RUNNING → SUCCEEDED/FAILED`를 짧은 트랜잭션의 `WHERE status=...` 갱신으로만 바꾸고, 갱신 행 수가 0이면 결과를 버린다(시간 초과 처리된 작업에 늦은 성공이 덮어쓰지 않게).
4. **마감 시각 하나**: 실행 시작 + 5분을 카탈로그 로딩·Gemini 재시도·아이콘 매칭 전체에 적용한다. 요청 제한은 `min(90초, 남은 시간)`.
5. **재시작 처리**: 앱이 뜰 때 남은 `QUEUED·RUNNING`은 모두 `FAILED(INTERRUPTED)`로 바꾼다. 자동으로 다시 돌리지 않고, 담당자가 다시 붙여넣는다. 10분 넘게 시작 못 한 작업은 `EXPIRED`, 오래 도는 작업은 `TIMEOUT`으로 조회 시 정리한다.

## 대안

- **동기 처리**: 단순하지만 요청이 1분 넘게 묶이고, 프록시·브라우저 시간 제한에 걸린다.
- **메시지 큐(Redis, SQS)**: 인스턴스 1대·담당자 1명 규모에는 과하다(근거 없는 기술은 넣지 않는다).
- **초안까지 저장**: 저장 시점의 선수·별칭에 묶여 낡는다.

## 결과

- 무료 한도 안에서 한 번에 하나씩 안전하게 돈다. 오래 걸려도 화면은 진행 상태를 보여 준다.
- 인스턴스가 1대라는 전제다. 여러 대로 늘리면 재시작 복구와 단일 실행기를 다시 설계해야 한다.
