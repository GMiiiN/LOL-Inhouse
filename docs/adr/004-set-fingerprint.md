# ADR 004. 세트 지문은 팀 순서와 무관한 정규 문자열로 만든다

- 상태: 확정 (M2, 2026-10-16)
- 관련: `docs/유저플로우.md` §5.1, 코드 `domain/set/SetFingerprint`

## 배경

같은 세트를 두 번 등록하면 통계가 두 배가 된다. 중복을 막을 "이 세트가 같은 세트다"라는 열쇠가 필요한데,

- 결과창에는 게임 ID가 숫자로 보이지 않고 복사 버튼만 있다. 그래서 AI가 읽을 수 없다(매치 ID는 수집하지 않기로 결정).
- 같은 경기를 이긴 팀 클라이언트에서 캡처할 수도, 진 팀 클라이언트에서 캡처할 수도 있다. 이때 화면의 **위쪽 팀이 서로 바뀐다**(위쪽 = 캡처한 사람의 팀).

## 결정

결과창에서 읽은 값 4가지로 지문을 만든다: **날짜, 경기 시간(초), 두 팀의 킬 합계와 골드 합계**.
두 팀 값은 위쪽/아래쪽 순서가 아니라 **(킬, 골드) 숫자 오름차순**으로 놓아 문자열로 잇는다.

```
2026-10-11|1094|8:29846|26:39852
날짜       |초  |작은 팀 |큰 팀   (킬:골드)
```

- 반대편 클라이언트에서 캡처해 위쪽/아래쪽이 뒤바뀌어도 문자열이 같다.
- 숫자로 비교한다. 문자열로 비교하면 "26" < "8"이 되어 순서가 뒤집힌다.
- 결정적 문자열이라 DB의 UNIQUE 컬럼에 그대로 넣을 수 있다(M3: `active_fingerprint` 생성 컬럼 + UNIQUE). 중복 검사 자체는 도메인이 아니라 DB가 맡는다. 동시 저장까지 막아야 해서다.
- 경기 시간은 `mm:ss` 문자열을 초로 바꿔 쓴다(분은 2~3자리, 초는 00~59).

## 대안

| 대안 | 버린 이유 |
|---|---|
| 매치 ID(Match-V5) | 결과창에 숫자로 안 보이고, 클라이언트에서 복사해야 해서 손이 많이 가며, 캡처한 사람과 등록하는 사람이 다르면 얻을 수 없다. 일반 API 자동 조회에도 의존하지 않기로 했다 |
| 이미지 해시 | 같은 세트라도 캡처 범위·클라이언트(승/패 팀)가 다르면 완전히 다른 파일이다. **같은 파일의 재업로드**만 막을 수 있어, 그 용도로는 별도로 쓴다(추출 전 1차 방어, M4) |
| 지문에 위쪽 팀 값을 먼저 넣기 | 구현은 쉽지만 반대편 캡처가 다른 지문이 되어 중복이 뚫린다 |
| 선수 id 목록까지 포함 | 닉네임 오인식·미등록 선수 연결 때문에 같은 세트가 다른 지문이 될 수 있다. 읽기 쉬운 숫자만 쓴다 |
| 해시(SHA 등)로 압축 | 현재 규모에서 길이 이득이 없고, 충돌 원인을 사람이 읽고 디버깅하기 어렵다 |

## 결과 · 한계

- 장점: 단순하고 결정적이며 사람이 읽을 수 있다. 샘플로 단위 테스트했다.
- 한계: 날짜·시간·킬·골드가 모두 같은 서로 다른 세트가 우연히 겹치면 등록할 수 없다. 19명 규모에서 매우 드물다고 보지만 **확률을 계산한 것은 아니다**(유저플로우 §5.1). 겹치면 예외 없이 등록 불가로 결정했다.
- 한계: AI가 숫자 하나를 잘못 읽으면 같은 세트가 다른 지문이 될 수 있다. 확인 화면에서 숫자를 수정할 수 있고, 팀 킬(K/D/A)·골드 합계는 선수 행 합계와 대조하는 경고(`SetDraftValidator`)로 한 번 더 걸러진다. 날짜와 경기 시간은 대조할 값이 없어서 이 경고로는 잡히지 않는다.
- 이후 변경: 지문 구성 요소를 바꾸면 이미 저장된 지문이 모두 달라진다. 되돌리기 어려운 결정이라 ADR로 남긴다.
