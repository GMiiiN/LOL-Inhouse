# 04. CI: GitHub Actions로 PR마다 자동 빌드·테스트

> 마일스톤 M1. 파일: `.github/workflows/ci.yml`

## 1. 무엇을 만들었나
`main`에 push하거나 PR을 올리면 GitHub가 서버(러너)를 빌려 **백엔드 테스트**와 **프런트 lint·테스트·빌드**를 자동으로 돌리는 설정.

## 2. 왜 이 구조인가
- **왜 CI인가**: "내 PC에선 됐는데"를 막는다. `.env`도, 설치된 MySQL도 없는 깨끗한 환경에서 돌아야 진짜로 재현 가능한 코드다. 운영 서버도 깨끗한 환경이다.
- **잡(job) 2개로 분리**: 백엔드와 프런트는 서로 의존하지 않아 **동시에** 돈다(시간 절약). 한쪽이 깨져도 다른 쪽 결과는 따로 보인다.
- **GitHub Actions 선택**: 저장소가 GitHub에 있고, 공개 저장소는 무료 사용량이 넉넉하다. 커리어 계획의 학습 순서(Docker→AWS→CI/CD)와도 맞다. 배포 자동화(M7)도 같은 도구로 이어 붙인다.
- **버린 대안**: Jenkins(서버를 직접 운영해야 함), 로컬 pre-commit 훅만 사용(사람이 건너뛸 수 있음).

## 3. 흐름
1. 개발자가 브랜치를 push하고 PR 생성
2. GitHub가 `.github/workflows/ci.yml`을 읽고 `pull_request` 이벤트에 맞는 워크플로를 시작
3. **backend 잡**: Ubuntu 러너 할당 → 코드 체크아웃 → JDK 21 설치 → Gradle 캐시 설정 → `./gradlew test`
   - 테스트가 Testcontainers로 MySQL 8.4 컨테이너를 띄움(러너에 Docker가 있음) → Flyway → JPA validate → `/actuator/health` 확인
4. **frontend 잡**(동시 진행): 체크아웃 → Node 22 설치(npm 캐시) → `npm ci` → lint → test → build
5. 두 잡 결과가 PR 화면에 체크(성공/실패)로 표시됨

## 4. 파일 지도
| 위치 | 역할 |
|---|---|
| `on: push(main) / pull_request` | 언제 도는지 |
| `jobs.backend` / `jobs.frontend` | 독립 실행 단위 |
| `defaults.run.working-directory` | 모노레포라서 명령을 각 폴더에서 실행 |
| `actions/checkout@v4` | 저장소 코드를 러너에 내려받기 |
| `actions/setup-java@v4` (temurin 21) | JDK 설치 |
| `gradle/actions/setup-gradle@v4` | Gradle 의존성 캐시 → 두 번째부터 빨라짐 |
| `actions/setup-node@v4` (`cache: npm`) | Node 설치 + `package-lock.json` 기준 캐시 |
| `npm ci` | lock 파일 그대로 정확히 설치(`npm install`과 달리 lock을 바꾸지 않음) |

## 5. 변수·설정 사전
- `DB_URL` 등은 CI에 없다. 그래서 `backend/src/main/resources/application.yml`에 `${DB_URL:기본값}` 형태의 **기본값**을 넣었다. 실제 접속 정보는 테스트 때 `@ServiceConnection`이 Testcontainers 컨테이너 주소로 덮어쓴다.
- `cache-dependency-path: frontend/package-lock.json`: 모노레포라 lock 파일 위치를 알려줘야 캐시가 동작한다.

## 6. 개념
- **러너(runner)**: 워크플로를 실행하는 일회용 가상 머신. 매번 새로 만들어지고 끝나면 버려진다.
- **액션(action)**: 재사용 가능한 단계(`uses:`). 버전(`@v4`)을 고정해 갑작스러운 변경을 막는다.
- **캐시**: 의존성을 매번 다시 받지 않도록 이전 실행 결과를 보관.
- **placeholder 기본값** `${KEY:default}`: 값이 없으면 `:` 뒤를 쓴다. 비밀번호는 기본값을 비워(`${MYSQL_PASSWORD:}`) 실수로 진짜 비밀번호를 코드에 쓰지 않게 했다.

## 7. 함정·디버깅
- **`.env`가 없으면 설정을 못 읽을 수 있다**: `${DB_URL}`처럼 기본값 없는 자리표시자는 값이 없을 때 오류가 날 수 있어 기본값을 넣었다. 확인 방법: 저장소를 `.env`가 없는 임시 폴더에 복사해 `./gradlew test` 실행.
- **실제로 겪음**: 그 임시 폴더에서 첫 실행은 `BUILD FAILED`, 다시 돌리자 통과(1건, 실패 0). 첫 실패의 원인 로그는 남기지 못했다(출력 끝부분만 확인함). Testcontainers 첫 기동·Gradle 첫 다운로드 같은 일시적 원인으로 추정하지만 확인되지 않았다. CI에서 같은 증상이 나오면 Actions 로그의 `Caused by`를 먼저 본다.
- 첫 Testcontainers 실행은 이미지 다운로드로 1분 이상 걸릴 수 있다.

## 8. 점검 질문
1. CI가 로컬 테스트와 다른 점은? → 깨끗한 환경, `.env` 없음, 매번 새 머신.
2. `npm ci`와 `npm install`의 차이는? → §4.
3. 백엔드 테스트가 CI에서 DB에 어떻게 접속하나? → Testcontainers가 띄운 컨테이너, `@ServiceConnection`이 주소 주입.
4. 잡을 둘로 나눈 이점은? → 병렬 실행, 실패 격리.
