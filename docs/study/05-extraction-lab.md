# 05. 결과창 AI 추출 실험 (M0)

> 도구: `tools/extraction-lab/` · 결정 기록: [ADR 003](../adr/003-extraction-approach.md)
> 1차 구현은 Codex, 빌드·실측·매칭 튜닝은 Claude. 수치는 2026-10-16 샘플 3장 기준.

## 1. 무엇을 만들었나

결과창 스크린샷을 넣으면 다음 순서로 처리하고 정답지와 비교해 정확도 리포트를 만드는 독립 Java 도구.

`PNG` → **Gemini**(구조화 JSON: 숫자·닉네임·날짜·시간·승패 + 초상화·밴 아이콘의 위치 박스) → 박스로 **잘라내기** → Data Dragon 공식 아이콘과 **이미지 비교**(챔피언 식별) → **정답지와 비교** → `out/report.md`, `out/report.json`

M4에서 이 코드를 백엔드 `com.lolinhouse.ingest`로 옮긴다.

| 항목 | 결과 |
|---|---|
| 모델 | `gemini-3.8-flash` (무료 등급) |
| 승패·날짜·경기 시간 | 3/3 |
| 팀 K/D/A·골드 합계 | 6/6 |
| 선수 K/D/A·CS·골드 | 30/30 (전부 정확) |
| 닉네임 | 26/30. 틀린 4개는 모두 **한 글자** 오인식(비슷한 한글 받침·모음, 비슷한 한자) |
| 픽 챔피언 | **29/29** (튜닝 후. 튜닝 전 28/29) |
| 밴 챔피언 | **20/30**, 정답이 3위 안 23/30 (튜닝 후. 튜닝 전 5/30) |
| 지연 | 재시도 없을 때 약 23초. 무료 등급 503(서버 혼잡)으로 재시도하면 36~66초 |

**2차 실행(리뷰 반영 후 같은 3장 재실행)**: 숫자 30/30, 닉네임 27/30, 픽 29/29, 밴 **17/30**(3위 안 23/30), 지연 43초(재시도 없음)~89초(503×2 + 429 후 성공).
→ 같은 이미지라도 **실행마다 결과가 달라진다**. Gemini가 매번 박스를 조금씩 다르게 잡고, 밴 매칭은 박스 위치에 민감하다. 닉네임도 한두 글자씩 달라진다. 그래서 "몇 퍼센트"는 한 번 재서 정할 수 없고 여러 번 재야 한다. 3위 안 비율(23/30)은 두 번 모두 같았다.

**주의: 픽·밴 수치는 같은 3장으로 설정을 고르고 같은 3장으로 잰 값**이다(과적합 위험). 새 결과창으로 다시 재야 실제 성능을 말할 수 있다. 샘플3 아래쪽 4행은 정답이 불분명해 제외했다(29개).

## 3. 왜 이 구조인가

### Gemini에는 "읽기"만 맡긴다
- 숫자·글자 읽기(OCR)와 아이콘 **위치** 찾기는 비전 모델이 잘한다. 실제로 숫자는 전부 맞았다.
- 결과창에는 챔피언 **이름이 글자로 없다**. 모델에게 이름을 맞히게 하면 "읽기 실수"와 "지식 실수"가 섞여 원인을 가려내기 어렵다. 그래서 챔피언은 라이엇 공식 아이콘(Data Dragon)과 **결정적으로 비교**해 얻는다(같은 입력이면 항상 같은 결과, 비용 0).
- 버린 대안: 모델에 이름까지 요청(나중에 밴의 보조 신호로 시험해 볼 여지는 있음), 고정 픽셀 좌표(Win+Shift+S로 캡처 범위가 매번 달라 깨짐).

### 구조화 출력(JSON 스키마)
자유 문장으로 받으면 다시 파싱하다 필드가 빠지거나 순서가 꼬인다. 스키마로 "팀마다 5행, 밴 박스 5개, 박스는 숫자 4개"를 강제하고, 받은 뒤에도 `validate`로 개수·형식·범위를 다시 검사한다. 스키마는 **모양**을 보장할 뿐 **값이 맞는지**는 보장하지 않는다 — 그래서 정답지 비교가 따로 필요하다.

### 픽과 밴은 비교 방식을 다르게 (`IconMatcher.PICK` / `IconMatcher.BAN`)
결과창에 그려지는 모양이 달라서다.

| | 결과창에서의 모양 | 그래서 한 처리 | 효과(1위 일치) |
|---|---|---|---|
| 픽 초상화 | **금색 원형 테두리** 안에 아이콘 가운데가 확대돼 보임 | 원 밖 무시(`circle`), 공식 아이콘 가장자리 8% 걷어냄(`iconInset`) | 22 → **29/29** |
| 밴 아이콘 | **사각 테두리** + 어둡게 처리 + 사선. 회색이 아니라 **색이 남아 있음** | 잘라낸 쪽 가장자리 12% 걷어냄(`cropInset`), 사선 띠 무시, 색으로 비교 | 1 → **20/30** |

두 경우 모두 "채널별 평균을 빼고" 비교한다. 밴은 전체가 어둡게 처리돼 있어서 밝기 자체가 아니라 **무늬(평균에서 벗어난 정도)**가 같아야 같은 챔피언이기 때문이다.

### 튜닝은 오프라인으로 (`MatchTuner`, `./gradlew tune`)
Gemini 호출은 장당 20초 이상이고 무료 한도도 있다. 그래서 한 번 실행해 잘라 둔 이미지(`out/crops/`)만으로 설정을 바꿔 가며 정확도를 다시 쟀다. 실험한 설정과 결과는 `MatchTuner`의 목록과 같다.

## 4. 흐름 — 어디서 어디로

1. `Lab.main` → 저장소 루트를 찾고, `Env`가 환경변수 또는 루트 `.env`에서 `GEMINI_API_KEY`, `GEMINI_MODEL`을 읽는다(출력 안 함).
2. `samples/*.png` 목록과 정답지 `samples/ground-truth.json`을 읽는다. 정답지는 **평가에만** 쓰고 프롬프트에는 넣지 않는다.
3. `DataDragon.load` → 최신 버전(이번엔 16.20.1)을 조회하고 그 버전의 챔피언 목록·아이콘 약 170개를 `cache/`에 받아 둔다(두 번째부터는 캐시 사용).
4. 이미지마다(사이 5초 대기): `Retry.extract` → `GeminiExtractor.extract`가 PNG + 지시문 + 스키마를 보내 JSON을 받고 `validate`.
5. `Comparison.teamWarnings` → 팀 합계와 행 합계가 다르면 경고.
6. `Lab.predictions` → `Boxes.crop`으로 초상화 10개·밴 10개를 잘라 `out/crops/`에 저장하고 `IconMatcher.match`로 1·2순위.
7. `Comparison.sample` → 정답과 필드별 비교. 실패한 이미지도 분모에 넣는다(성공한 것만 세면 정확도가 부풀려짐).
8. `Lab.write` → `out/report.json`, `out/report.md`.
9. (튜닝) `MatchTuner` → `out/crops/` + 정답지로 설정별 정확도·정답 순위 출력.

이번 도구는 결과창 **화면 순서** 그대로 다룬다. 포지션 배정·진영·밴 전체 순서(B1 R1…)·선수 연결은 M2 도메인 규칙에서 한다.

## 7. 개념

- **구조화 출력**: 모델 응답의 모양을 스키마로 계약. 값의 정확도는 별개.
- **정규화 좌표**: 이미지 크기와 상관없는 비율 좌표. 원본 크기를 곱해 픽셀로 바꾼다.
- **결정적 비교 vs 생성**: 같은 입력에 항상 같은 답(비교) vs 매번 달라질 수 있는 답(생성).
- **평균 제거(정규화)**: 밝기가 전체적으로 다른 두 이미지에서 무늬만 비교하는 방법.
- **과적합**: 같은 데이터로 설정을 고르고 같은 데이터로 평가하면 실제보다 좋게 나온다. 처음 보는 데이터로 재검증해야 한다.
- **지수 백오프**: 503·429를 받으면 바로 다시 보내지 않고 대기 시간을 늘려 가며 재시도.

## 8. 함정·디버깅 (실제로 겪은 것)

1. **Codex 환경의 네트워크 차단**: Codex는 Maven·Gemini·Data Dragon 연결이 막혀 컴파일조차 못 했다(`Permission denied: getsockopt`). → 빌드·실측은 네트워크가 되는 쪽에서 하기로 역할을 나눔.
2. **SDK 메서드 오용(컴파일 오류)**: `responseSchema(Map)`은 SDK의 `Schema` 타입만 받는다. JSON 스키마를 Map으로 넘기려면 `responseJsonSchema(Object)`. 원인 확인은 `javap`로 SDK 클래스의 메서드 목록을 직접 봤다.
3. **모델 404**: `gemini-2.5-flash` 호출이 3장 모두 404. 모델 목록 API에는 보이지만 실제 호출 메시지는 "신규 사용자에게 더 이상 제공되지 않음, 3.8-flash 사용". → `.env`의 `GEMINI_MODEL`만 바꿔 해결(설정으로 뺀 덕분에 코드 수정 없음).
4. **503 서버 혼잡**: 무료 등급에서 2장이 각각 2~3번 503 후 성공. 재시도가 없었다면 실패했을 것.
5. **밴은 회색이 아니었다**: 처음엔 "밴=회색"이라 보고 명암만 비교해 5/30. 잘라낸 이미지를 직접 보니 색이 남아 있고 사각 테두리가 있었다. 테두리 제거 + 색 비교로 20/30.
6. **원형 테두리**: 픽 초상화의 금색 원 테두리가 오차를 키웠다. 원 밖을 무시하자 29/29.
7. **사람 눈 판단도 틀린다**: 처음 크롭을 보고 "1행은 이즈리얼이 아닐 것"이라 판단했지만 정답은 이즈리얼(스킨 때문에 달라 보임). 정답지 없이 눈으로 판정하지 않는다.
8. **Windows 콘솔 한글 깨짐**: `./gradlew run` 출력이 깨졌다(콘솔 코드페이지). 결과는 UTF-8로 쓴 `out/report.*`에서 확인.
9. **Codex 코드 리뷰로 고친 것** (원인 → 조치):
   - 응답의 `rows`가 원소 5개짜리 **객체**여도 `size()==5`라 검증을 통과 → `isArray()` 검사 추가.
   - 박스 좌표 `4294967296` 같은 큰 수가 `asInt()`에서 0으로 잘려 범위 검사를 통과 → `canConvertToInt()` 먼저 확인.
   - `2026/02/31`도 정규식은 통과 → `LocalDate` 엄격 파싱(`ResolverStyle.STRICT`, 연도는 `uuuu`)으로 실제 날짜만 허용.
   - `MatchTuner`가 정답지 **순번**과 crop **번호**를 같다고 가정 → crop 이름을 샘플 **파일 이름** 기준(`1-top-row-1.png`의 `1`은 `1.png`)으로 바꾸고 정답지의 `file`로 짝을 맞춤.
   - 정답 id가 아이콘 목록에 없으면 순위 계산이 배열 −1 접근으로 중단 → 따로 모아 출력.
   - crop 실패가 경고로만 남아 상태가 "완료" → 실패가 있으면 "일부 실패".
   - 실패 원인 구분 불가 → 이미지마다 실패 **단계**(`errorStage`: 이미지 읽기 / Gemini 추출·검증 / 팀 합계 검사 / 아이콘 자르기·매칭) 기록. SDK 원문 메시지는 키가 섞일 수 있어 여전히 저장하지 않음.
   - `DataDragon`이 만든 `HttpClient`를 닫지 않음 → `AutoCloseable`로 만들고 try-with-resources로 닫음.
   - 회귀 테스트 2개 추가(날짜·배열·큰 좌표). 테스트 총 11개.
   - 보류: `Retry`가 실제 시간·난수에 묶여 재시도 테스트가 어렵다 → M4에서 백엔드로 옮길 때 대기·시계를 주입하는 구조로 바꾸고 테스트한다.

## 9. M4에 주는 결론

- **숫자·경기 정보**: 자동 채움을 믿어도 된다. 다만 팀 합계 검사는 계속 둔다.
- **닉네임**: 등록된 선수는 유사도 매칭으로 한 글자 오인식을 흡수. 처음 보는 닉네임은 확인 화면에서 눈에 띄게.
- **픽 챔피언**: 자동 채움 + 확인 화면에서 아이콘으로 한눈에 확인.
- **밴 챔피언**: 1위만 믿으면 3개 중 1개꼴로 틀린다. 확인 화면에서 **상위 3개 후보 + 검색**으로 고르게 하고, 1·2순위 차이가 작으면 강조.
- **지연**: 장당 20~40초, 무료 등급 혼잡 시 1분 이상. 확인 화면 진입 전에 진행 표시가 꼭 필요(등록 순서 변경은 "개선 후보"로 보류). 503·429 재시도는 필수.
- **변동성**: 같은 이미지도 실행마다 박스·닉네임이 조금씩 달라진다. 밴은 후보 3개를 보여주는 설계가 1위만 믿는 것보다 안정적이다(두 번 모두 3위 안 23/30).
- **다음 검증**: 새 결과창으로 같은 설정이 유지되는지 재측정.

## 10. 점검 질문
