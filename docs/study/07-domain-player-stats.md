# 07. 선수 닉네임 매칭 · 통계 도메인 규칙 (M2)

패키지: `backend/src/main/java/com/lolinhouse/domain/player/`, `.../domain/stats/` (순수 Java, Spring·DB 없음)
테스트: `backend/src/test/java/com/lolinhouse/domain/player/`, `.../domain/stats/` (총 93개: player 57, stats 36)

## 1. 무엇을 만들었나

1. **닉네임 매칭**: AI가 읽은 닉네임을 알려진 별칭 목록과 비교해 `EXACT`(정확 일치) / `TRUNCATED_AUTO`(잘린 닉네임 자동 연결) / `CANDIDATES`(담당자가 고를 후보) / `NEW_UNREGISTERED`(미등록 선수 새로 생성) 중 하나로 분류한다. 표시 이름 규칙(미등록=닉네임, 등록=실명)도 작은 값 객체로 만들었다.
2. **통계**: 세트 기록(`PlayerSetRecord`) 목록에서 누적 KDA, 세트 승률, 참여율, 포지션별·챔피언별 집계, 대결 개인 결과(승·무·패), 전체/포지션별 랭킹을 계산한다.

둘 다 "입력 값 → 결과 값"만 있는 순수 함수라, DB 없이 JUnit만으로 빠르게 검증된다. M3(영속성)·M4(추출 파이프라인)·M5(조회)가 이 규칙을 그대로 가져다 쓴다.

## 2. 왜 이 구조인가

### 정규화 (NFKC + 공백)
OCR 결과와 등록 닉네임이 **보이는 모양은 같은데 코드가 다른** 경우가 있다(전각 `Ａ` vs `A`, 반각 가타카나 `ｶﾞ` vs `ガ`, 전각 공백 `U+3000`, 연속 공백). 비교 전에 양쪽을 같은 표준형으로 맞춘다.
- NFKC: 호환 문자를 표준 문자로 합친다. 한글·한자·가나는 그대로 둔다.
- 공백: 앞뒤 제거(NBSP·U+202F·전각 공백 포함) + 내부 연속 공백 하나로.
- **대소문자는 구분하지 않는다(사용자 결정 2026-10-16)**. 그래서 함수가 둘이다. `normalize`는 화면·저장용(대소문자 유지), `comparisonKey`는 비교용(`normalize` 결과를 `Locale.ROOT`로 소문자화). 새 미등록 선수의 표시 이름과 후보의 별칭 표기는 원래 대소문자를 그대로 쓴다. **M3의 "정규화 닉네임 UNIQUE 키"는 반드시 `comparisonKey`와 같은 규칙으로 만든다**(원본 닉네임 컬럼에만 UNIQUE를 걸면 `Faker`/`faker`가 둘 다 들어간다).
- 버린 대안: 특수문자 제거(서로 다른 닉네임이 같아질 위험), 형태소 분석(과함).

### 편집 거리(Levenshtein)와 임계값 0.70 / 0.5
- **편집 거리**: 한 문자열을 다른 문자열로 바꾸는 최소 삽입·삭제·치환 횟수. 사진 속 한 글자 오인식(M0 실측: 닉네임 오류 4개가 모두 한 글자 치환)이 거리 1로 정확히 잡힌다.
- **유사도** = `(긴 길이 - 거리) / 긴 길이` (= `1 - 거리/길이`).
- **0.70 (자동 연결, 잘린 닉네임만)**: 문서(유저플로우 §3.3)가 정한 값. 짧게 보이는 앞부분(예: 10글자)에서 3글자까지 틀려도(7/10) 연결하는 느슨한 값인데, 그래도 되는 이유는 "내전 인원 안에서 닉네임이 겹치지 않는다"는 사용자 결정 + "0.70 이상인 선수가 정확히 한 명이어야 한다"는 안전장치 때문이다(1등이 2등보다 높기만 해서는 부족하다: 2등도 0.70 이상이면 사람이 고른다).
- **0.5 (후보 노출)**: 문서에 값이 없어 정한 값(가정). 자동 연결이 아니라 담당자가 눈으로 고르는 후보라서 느슨해도 안전하다. 4글자 닉네임에서 두 글자 틀린 경우(0.5)까지 보여주고, 그 아래는 무관한 닉네임이라 잡음이 된다. 최대 3명.
- **왜 전체 닉네임의 "비슷한 것"은 자동 연결하지 않나**: 앞부분만 보이는 잘린 닉네임은 정보 자체가 부족해서 어쩔 수 없이 자동 연결을 허용했지만, 전체 닉네임은 정보가 다 있다. 한 글자 차이는 (a) OCR 오인식 (b) 실제로 다른 사람/부계정, 둘 다 가능하다(문서: "부계정·닉네임 변경·오인식 구분"). 컴퓨터가 구분할 수 없으니 사람이 고르게 한다. 잘못 합치면 두 선수의 전적이 섞이고, 되돌리기 어렵다.
- 버린 대안: Apache Commons Text(`LevenshteinDistance`). 의존성을 늘릴 만큼 복잡한 코드가 아니고(30줄), 배우려는 개념이라 직접 작성했다. `build.gradle`은 바꾸지 않았다.

### 누적 KDA (평균 KDA가 아닌 이유)
`총(K+A) ÷ 총D`. 판마다 KDA를 구해 평균 내면 **데스가 적은 판 하나가 평균을 끌어올린다**(예: 7.5와 0.75의 평균 4.125, 실제 누적은 21/10 = 2.1). 누적 방식이 "실제로 한 일의 총합" 대비 비율이라 판 수가 많은 쪽이 더 믿을 만하다. `KdaTest.sumAddsTotalsNotRatios`가 이 차이를 고정한다.

### 세트 기준 승률
`이긴 세트 수 ÷ 참여한 세트 수`. 대결(최대 N세트) 단위 승패로 바꾸지 않는다(문서 §2·§8.3). 대결 개인 결과(WIN/DRAW/LOSS)는 별도 표시용이다.

### PERFECT를 값이 아니라 상태로 모델링
데스 0이면 나눗셈이 `Infinity`가 된다. `Infinity`를 그대로 두면 `Double.compare`·JSON·화면에서 조용히 이상하게 동작한다. 그래서 `Kda.isPerfect()`로 명시하고, `ratio()`는 PERFECT에서 호출하면 예외를 던져 "숫자인 척"하는 실수를 막는다. 정렬은 `RankingCalculator.compareKda` 한 곳에서만 PERFECT를 다룬다.
- **정렬 규칙(사용자 결정 2026-10-16)**: 정렬값 = (K+A) ÷ max(D, 1). 데스 0은 데스 1로 보고 **정렬에만** 쓰고, 화면 표시는 계속 "PERFECT"다. 그래서 K+A가 작은 PERFECT가 큰 숫자 KDA 위로 튀어 오르지 않고, 데스 1인 같은 합계와 동률이다.

### 최소 표본 N
사용자 결정(2026-10-16): 단위는 **세트**, 기본값 **5**(`RankingCalculator.DEFAULT_MIN_SETS`). 값은 여전히 `minSets` 파라미터라 호출자가 바꿀 수 있고, 인자를 생략한 오버로드는 기본값을 쓴다. 미달 선수도 기록은 표시하고 순위만 비운다.

## 3. 흐름

### 닉네임 (M4 추출 파이프라인이 호출할 예정)
```
AI가 읽은 닉네임 문자열(끝에 "…" 가능)
 → NicknameMatcher.match(닉네임, 알려진 별칭 목록)
    1) 양 끝 유니코드 공백 제거 후 "…"로 끝나는지 먼저 확인 (정규화 전에!)
    2) 정규화(NFKC·공백)와 비교 키(소문자) 만들기
    3) 잘리지 않았으면: 키가 같은 별칭의 선수가 정확히 한 명 → EXACT
         서로 다른 선수 둘 이상이 같으면 → CANDIDATES(모두, 유사도 1.0)
    4) 선수별로 가장 비슷한 별칭 하나만 남겨 유사도 순으로 정렬
         잘림: 보이는 앞부분 vs 별칭의 같은 길이 앞부분
         전체: 닉네임 전체 vs 별칭 전체
    5) 잘림 + 유사도 ≥ 0.70인 선수가 정확히 한 명 → TRUNCATED_AUTO(그 선수, 유사도)
    6) 유사도 ≥ 0.5 상위 3명 → CANDIDATES (확인 화면에서 담당자가 선택)
    7) 없으면 NEW_UNREGISTERED (표시 이름 = 정규화한 닉네임(대소문자 유지), 잘린 닉네임이면 fullNicknameRequired=true)
    * 입력이 잘렸다면 어떤 결과 종류든 fullNicknameRequired=true (후보를 모두 거부하고 새 선수를 만들 때 필요)
```

### 통계 (M5 조회가 호출할 예정)
```
세트 기록 목록(List<PlayerSetRecord>)
 → PlayerStats.overall / byPosition / byChampion / participationRate / duelResult  (선수 프로필)
 → RankingCalculator.overall / byPosition(records, 포지션, minSets, 정렬키)         (랭킹)
      선수별로 묶기 → StatSummary 계산 → 최소 표본으로 나눔 → 비교기로 정렬 → 공동 순위 부여
```

## 6. 개념 설명

### 편집 거리 손계산 (`fax` → `foxy`)
`D[i][j]` = `fax`의 앞 i글자를 `foxy`의 앞 j글자로 만드는 최소 횟수. 각 칸은 **대각선(치환, 같은 글자면 +0 다르면 +1) / 위(삭제 +1) / 왼쪽(삽입 +1)** 중 최솟값이다.

|   | (빈) | f | o | x | y |
|---|---|---|---|---|---|
| (빈) | 0 | 1 | 2 | 3 | 4 |
| f | 1 | 0 | 1 | 2 | 3 |
| a | 2 | 1 | 1 | 2 | 3 |
| x | 3 | 2 | 2 | 1 | 2 |

오른쪽 아래 칸 = 거리 2 (`a→o` 치환 1회 + `y` 삽입 1회). 긴 길이 4이므로 유사도 = (4 − 2) / 4 = 0.5. 코드는 표 전체를 만들지 않고 윗줄(`previous`)과 현재 줄(`current`) 두 줄만 번갈아 쓴다.

### NFKC
유니코드 정규화 방식 중 하나. K(Compatibility)는 "모양만 다른 호환 문자"(전각 영문, 반각 가타카나, `①` 등)를 표준 문자로 바꾸고, C(Composition)는 분리된 글자(`ガ` = `カ`+`゛`)를 합친다. 한 글자씩 비교하는 편집 거리 앞에서 반드시 필요하다.

### 코드포인트 단위
자바 `String.length()`는 UTF-16 `char` 개수다. 𠮷 같은 보조 평면 한자는 char 2개다. 그대로 비교하면 "한 글자 오인식"이 거리 2로 계산되어 임계값 판정이 어긋난다. 그래서 `codePoints()`로 글자 단위 배열을 만든다.

### 비교기(Comparator) 체인
`primary.thenComparing(승률).thenComparing(세트 수).thenComparing(KDA)`: 앞 비교가 0(같음)일 때만 다음 비교로 넘어간다. 전체를 `reversed()`하면 내림차순. 체인이 끝까지 0이면 "완전 동률"이고, 이 비교 결과 그대로 공동 순위를 판정한다(정렬 기준과 동률 기준이 하나라서 어긋나지 않는다). `List.sort`는 안정 정렬이라 동률끼리는 입력 순서를 유지한다.

### 공동 순위 (1,1,3)
앞 사람과 비교기가 0이면 앞 사람 순위를 그대로, 아니면 자기 위치(인덱스+1). 두 명이 1위면 다음은 3위.

### TDD로 진행한 순서
1. 테스트 파일을 먼저 작성 → `gradlew test` 실행 → **컴파일 실패**(클래스 없음)로 빨간불 확인. (컴파일 오류도 TDD의 첫 빨간불이다. 시그니처가 테스트로 먼저 확정된다.)
2. 최소 구현 작성 → 같은 명령으로 초록불.
3. 경계값 테스트를 따로 둠: 정확히 0.70(자동 연결), 9/13 = 0.692(후보), 정확히 0.5(후보 포함), 동점 2명(자동 연결 금지).
4. 주의: 이번 구현은 테스트를 한꺼번에 먼저 쓰고 구현을 한꺼번에 했다(클래스 단위). 규칙마다 빨강→초록을 한 개씩 돌지는 않았다. 실패 테스트가 정말 그 규칙 때문에 실패하는지(구현을 일부러 틀리게 해 보는 변이 확인)는 하지 않았다.

## 7. 함정과 디버깅

- **`…`는 NFKC에서 `...`가 된다**(U+2026 → 점 3개). 정규화부터 하면 "잘렸는지"를 판별할 수 없다. 그래서 `trim` 직후, 정규화 **전에** `…`로 끝나는지 본다. 구현 전에 알고 설계했고, 잘린 닉네임 테스트들이 이 순서를 지켜 준다(순서를 바꾸면 TRUNCATED_AUTO 테스트가 깨진다는 것을 코드 읽기로 확인, 실제로 바꿔 실행하지는 않음).
- **`1 - 거리/길이`의 부동소수점**: 경계값(정확히 0.70)에서 어긋날 수 있어 `(길이 - 거리)/길이`로 나눗셈을 한 번만 한다. 같은 실수값의 나눗셈은 같은 double이 되기 때문이다. 이것도 사전 대응이며 경계 테스트(7/10 → `isEqualTo(0.7)`)가 통과함을 확인했다.
- **같은 선수의 별칭이 여럿**: 별칭마다 후보를 만들면 "1등과 2등이 같은 선수"가 되어 자동 연결이 막히고 후보 목록에 같은 사람이 두 번 나온다. 선수당 가장 비슷한 별칭 하나로 합친 뒤 순위를 낸다(테스트 2개).
- **bash 도구에서 여러 파일을 한 번에 heredoc으로 쓰다 실패**: 따옴표·한글이 섞인 긴 heredoc이 "unexpected EOF"로 통째로 실행되지 않았고 파일도 하나도 안 만들어졌다. 파일 생성 도구로 한 파일씩 쓰는 쪽으로 바꿔 해결했다. 실행 전에 만들어졌는지 `ls`로 확인하는 습관이 필요하다.
- **PERFECT는 `Infinity`가 아니다**: `ratio()`가 PERFECT에서 예외를 던지게 해서, 정렬 코드 외에서 실수로 숫자로 쓰면 바로 드러나게 했다.

- **테스트 실행 환경 메모**: 다른 패키지(`domain.set`)가 수정 중이어서 `gradlew test`의 테스트 컴파일이 통째로 깨진 시간이 있었다. 이때 내 패키지만 `javac` + JUnit 런처로 따로 빌드해 빨강(9개 실패)과 초록을 확인한 뒤, 컴파일이 복구되고 나서 `gradlew test` 전체를 다시 돌렸다.

### 문서와 결정 사항
- **PERFECT 정렬·최소 표본·대소문자**: 문서가 비워 둔 항목을 사용자가 2026-10-16에 정했다(정렬값 (K+A)/max(D,1), 최소 5세트, 대소문자 무시). 정렬 규칙은 `RankingCalculator.compareKda` 한 곳이라 바꾸려면 거기만 고친다.
- **후보 임계값 0.5, 후보 수 3**은 요청 사양에서 온 값이며 문서에는 없다.
- **잘린 닉네임인데 0.70 미만 + 0.5 이상** → 후보로 보여준다(앞부분 유사도 기준). 문서에는 이 구간이 없어 후보 규칙을 잘림에도 적용했다.
- **유저플로우 §3.3 흐름도의 "후보 선수의 새 닉네임인가?" 분기**(후보에 연결하며 닉네임 추가 vs 미등록 생성)는 매처가 아닌 확인 화면·담당자 선택의 일이라 여기서 다루지 않았다.

## 8. 스스로 점검할 질문

1. 왜 `…` 판별을 정규화보다 먼저 하나?
   → NFKC가 `…`를 `...`로 바꿔 잘림 표시가 사라지기 때문.
2. 잘린 닉네임 `Moonlight…`이 별칭 `Moonlight_Fox`, `Moonlight_Cat` 둘 다와 100% 일치하면?
   → 0.70 이상인 선수가 둘이라 유일하지 않으므로 자동 연결하지 않고 CANDIDATES. (`truncatedTieBetweenTwoPlayersIsNotAutoLinked`, 1.0과 0.8처럼 점수가 달라도 마찬가지: `truncatedIsNotAutoLinkedWhenSecondPlayerIsAlsoAboveThreshold`)
3. 전체 닉네임에서 한 글자 틀린 92% 유사 닉네임을 왜 자동 연결하지 않나?
   → OCR 오인식인지 다른 사람(부계정 등)인지 구분할 수 없고, 잘못 합치면 전적이 섞여 되돌리기 어렵기 때문.
4. `fax`와 `foxy`의 편집 거리와 유사도는?
   → 2, 0.5 (§6 표).
5. 판별 KDA를 평균 내면 왜 안 되나? 예를 들어 설명하라.
   → (10/2/5)와 (2/8/4)에서 판별 KDA는 7.5와 0.75, 평균 4.125. 누적은 (12+9)/10 = 2.1.
6. `1 - d/n` 대신 `(n - d)/n`을 쓴 이유는?
   → 경계 비교(≥ 0.70)에서 반올림 오차를 피하려고 나눗셈 한 번만 하기 위해.
   * 추가: `Faker`와 `faker`는 같은 선수로 취급하나? → 예(EXACT). 비교 키가 소문자라서다. 그럼 서로 다른 두 선수가 `Faker`/`faker`를 각각 가지면? → CANDIDATES(모호하니 사람이 고른다).
7. 데스 0인 선수의 KDA를 어떻게 표현하고, 랭킹에서 어디에 두나?
   → `Kda.isPerfect()` 상태로 표현. 정렬할 때만 데스를 1로 보고 (K+A)/max(D,1)로 비교(사용자 결정 2026-10-16). 표시는 PERFECT.
8. 승률 동률일 때 순서는? 모두 같으면?
   → 세트 수 → KDA. 모두 같으면 공동 순위(1,1,3).
9. 포지션 랭킹은 전체 랭킹과 무엇이 다른가?
   → 해당 포지션으로 실제 뛴 세트만 기록으로 삼고 최소 표본도 그 세트 수로 적용. 전체 10세트인 선수도 MID가 1세트면 MID 랭킹에선 표본 미달.
10. 1승 1패인 대결의 개인 결과와 세트 승률은?
    → DRAW, 50%. (`oneWinOneLossInDuelIsDrawWithFiftyPercent`)
11. 미등록 선수를 나중에 실명으로 등록하면 전적이 분리되지 않나?
    → 선수 ID가 같고 표시 이름만 `PlayerName.register`로 바뀌므로 분리되지 않는다.
12. `ratio()`가 PERFECT에서 예외를 던지는 이유는?
    → 데스 0을 `Infinity` 같은 숫자로 흘려보내지 않고 호출자가 `isPerfect()`를 먼저 확인하게 강제하기 위해.
